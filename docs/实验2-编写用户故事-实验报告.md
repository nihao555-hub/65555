# 实验2 编写用户故事及其验收测试标准 · 实验报告

- 项目：智星校园 — AI 智能校园生活助手
- 演讲人：欧阳晨旭
- 日期：2026.06

## 一、实验目的

1. 掌握编写用户故事的方法和实践。
2. 加深理解用户故事需要遵循的 INVEST 规则。

## 二、实验内容与过程

基于智星校园项目（新版本开发），选定 3 个需求（二手交易、失物招领、AI 智能课程表），假定一个迭代为两周：

1. 学习用户故事模板：As a〈User Type〉I want〈achieve goal〉So that I can〈get some value〉。
2. 逐个需求分析讨论，按 INVEST 原则拆分编写用户故事。
3. 编写每个用户故事的同时编写验收测试用例。
4. 重复以上步骤直到 3 个需求全部拆分完毕，共得到 10 个用户故事（见《实验2-用户故事清单.md》）。

## 三、INVEST 规则的应用体会

| 规则 | 应用体会 |
|------|----------|
| Independent 独立性 | 把"发布物品并搜索物品"拆成 US-01 与 US-02，两者可独立交付 |
| Negotiable 可谈判 | 故事只写目标与价值，留言提醒方式等细节在迭代中协商 |
| Valuable 有价值 | 每个故事的"原因是"都写出用户价值，删掉了纯技术性条目 |
| Estimable 可估计 | 故事拆小后，每个都能拆任务并估算出 1-3 天的工作量 |
| Sized Right 合理尺寸 | 所有故事颗粒度不超过 1 个 sprint（2 周） |
| Testable 可测试 | 每个故事附 2-4 条验收测试用例，定义通过标准后才算编写完毕 |

## 四、经验与教训

1. **不要在故事里用 And / Or**：初稿"学生可以发布并管理物品"含分支任务，拆成发布（US-01）与下架（US-04）后估算立刻清晰。
2. **故事不写技术**：第一版 US-06 写了"用向量数据库做匹配"，违反规则——技术属于 Task，不属于 Story，改为只描述"获得 AI 匹配建议"。
3. **验收用例是故事的灵魂**：先写验收用例再写实现，开发时不会跑偏，演示时直接按用例逐条验收。
4. **拆分粒度需要反复协商**：颗粒度太大无法估算，太小失去价值，"一个迭代能完成、能独立演示"是最实用的判断标准。
